# Decisions

One line per decision that still shapes the package. Each is settled; reopening one is a new discussion, not a bug.

## Content model

- Localized values are always a map inside the field, even with one locale: texts `{ es, en }`, media `{ es: id, en?: id }`; a plain value found in storage moves to the default locale in `withDefaults`.
- A missing text in a non-default locale keeps the document out of the publication; a missing media version reuses the original (`null` and `[]` both mean "inherit").
- Buttons localize only their label; opening hours only their note; everything else is shared unless the field says `localized: true`.
- Media alt text and caption are jsonb per locale; the default locale's alt is required on upload, the others at publish.
- Slugs live in `slugs jsonb` per locale; the `slug` column stays as the default locale's mirror (documented in the migration and `editing.ts`) until 1.0.
- Internal links are references (`type: 'entry'` with `entry`, `id`, `anchor`); a free path is `type: 'internal'`. Rich text images keep only `mediaId`.
- Validation is the package's own: issue codes translated by the catalogs, no Yup. Error paths include the locale (`hero.title.es`), matching the stored shape.
- A `new` or `changed` document with missing content displays as `incomplete`; the stored status does not change.
- `publish_log.error_code` has no CHECK constraint on purpose, so a new code (`build_cancelled`) needs no migration.

## Field kinds and catalogs

- One `defineField` per kind, typed through `FieldTypes<F>`; built-in kinds use the same mechanism as project kinds.
- Core holds no panel inputs: a lazy `import()` in core would drag PrimeReact and Sass into the proxy and site bundles. Inputs live in a `'use client'` map in the panel; project kinds register theirs in `createCmsClient({ inputs })`. Resolution: `field.component`, then the project's input, then the package's.
- Catalogs are TypeScript objects per locale; `es` is the mold and `en` `satisfies` it. Every user-facing text comes from a catalog (`texts.test.ts` fails on literals) and a project overrides keys with `messages`.
- Server actions return catalog keys as errors, never prose; the panel translates.

## Wiring

- The project owns `src/cms/server.ts`: `createCmsServer({ config, supabase, publishTarget, logger })` reads the project's `process.env`; the package reads none. `cms.config.ts` is imported by the browser, the proxy and the site, so it holds no secrets.
- Panel routes, `src/cms/actions.ts` and the API handlers are generated by `linkchar-cms routes` with a marker line; files without the marker belong to the project.
- Route segments default to Spanish and are configurable with `paths`; the proxy matcher and the segments stay literals because Next reads them statically.
- `server-only` is declared once, in `server/index.ts`. ESLint layer zones keep `core`, `site`, `publish`, `server` and `panel` apart.
- `withCms` reads the redirects at `next build`; it detects `next typegen` through `process.argv` because `NEXT_PHASE` is set only after `redirects()` has run. `redirects: false` is the escape hatch.
- `sitemap()` throws without `site.url`; `absoluteUrl` still returns relative paths for metadata. A page's `lastModified` also counts the entries its sections declare in `uses`, not the singletons it previews (menu, footer).
- Site readers show drafts only in Draft Mode and only to whoever may open the preview (`canPreview`: signed in, active, past the second factor), checked against Auth on each request.
- Site defaults for metadata are fields of a page or singleton (`site.defaults`), so editors change them; that makes `cms.site.metadata()` async. The page's own SEO always wins.
- The project registers its generated `Database` as `Register.database` for its own tables (`cms.supabase()`, `cms.supabaseAdmin()`); the package's queries stay typed against its own types.
- `DraftRefresh` and the schema.org helpers live in `site`; project-specific nodes (a clinic, an FAQ) stay in the project.
- Invitation and recovery email templates belong to each project (`supabase/templates`), because Supabase's defaults link to a route the panel does not serve.

## Panel

- Formik stays, with the core validators; PrimeReact runs unstyled with the package's passthrough; the theme is a Tailwind 3 preset with `cms-` tokens and `color-mix()` derivations.
- Never copy props into state during render in panel components: a poll that sets equal values leaves stale updates React replays over fresh props (`PublishStatus`, 0.3.x).
- The header counts only the changes the next publish takes; the editor announces each save (`cms:saved`) and the header refreshes, instead of `router.refresh()` per autosave.
- Guided tours have neutral ids (`welcome`, `pages`, `document`…) and never start while a field has the focus.
- The duplicate check hashes the original file (SHA-256), not the processed blob: the canvas WebP differs per browser.
- Untouched drafts are purged on reading a collection list, only when revision 1, equal timestamps, data equal to the schema defaults and no usage.

## Dependencies and releases

- `dependencies` and `devDependencies` are exact; `peerDependencies` are caret ranges, because each project pins its own versions and exact peers turn a patch difference into a conflict.
- Held back on purpose: PrimeReact 11 and primeicons 8 (paid versions: never), Tailwind 4 (and tailwind-merge 3: a migration for every project), TypeScript 7 (typescript-eslint supports `<6.1`), `@types/node` majors beyond `engines.node`.
- `@supabase/ssr` stays 0.x; the peer `^0.12.0` accepts only 0.12.x, so each new minor of it needs a package release.
- Core export pruning waits for 1.0.
- One changeset per change; releases through the version PR, which CI gates with `publint` and the tarball check.
